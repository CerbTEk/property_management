# Payment and refund CSV migration

Bookings → Import payments and refunds records completed USD export transactions for already imported bookings in one selected listing. The header-only template supports 200 records / 512 KB. Map all 13 columns: original transaction ID, original booking ID, guest, arrival, departure, guest count, payment/refund type, amount, USD currency, completed UTC date, channel/bank/cash/other method, reference and original parent payment ID. Payment parent values are blank; refunds require a parent ID. Pending records, host payouts, adjustments, reversals and currency conversion are unsupported. Use guest payment/refund amounts before host channel fees, not net payout figures.

The preview validates exact cents, guest/stay identity, original reservation links, references, dates and refund dependencies. Payments run before refunds independent of CSV order. A refund can use a payment in the same file or a prior import for the same booking/source. Cumulative active refunds cannot exceed the parent's remaining recorded amount, and refund dates cannot precede payment dates. Repeated original IDs, repeated type/reference values, missing parents and cross-booking links block the entire batch. Values accept up to two dollar decimals and $10 million per transaction. Future dates use server UTC, matching the existing ledger.

New payment records require confirmed bookings, preserving existing ledger rules. Refunds on cancelled bookings are supported when the payment was previously imported and guest/stay details still match. Importing a cancelled booking's previously unrecorded historical payment requires a separate settlement workflow and is not supported here. Bookings with any manually entered transaction history, including corrections, reject new imports until separate reconciliation; no automatic manual-record linking is offered. This avoids silently double-counting payments that lack original export receipts.

The SECURITY INVOKER `ts_import_transactions` RPC locks the owned listing/bookings, validates the full payload, orders dependencies, and calls the existing transaction RPC with current sequence and a server-generated request UUID. The immutable `ts_transaction_imports` receipt uniquely scopes owner/source/original transaction ID and binds the saved ledger transaction, booking, listing and original normalized snapshot. Its trigger verifies the owned reservation origin, matching transaction data and refund payment link. Owner/MFA RLS applies with the existing pilot exception; anonymous access and receipt updates/deletes are denied. New records and receipts save in one transaction; any failure rolls everything back.

Identical receipt replay skips despite later cancellation, guest edits or manual corrections. Changed original snapshots require normal ledger review and never restore or modify history. The existing ledger's host-recorded evidence remains explicit. Imported records feed booking balances and dated Reports, including cancellation/refund records; no funds move, no processor verification is claimed, and no financial charge revision or tax determination is created.

No real export format or payout semantics have been validated because no actual source CSV has been supplied. Source column names are mapped by the host. Real guest/payment records are not imported during deployment. Automated checks cover order-independent links, cents, cumulative refunds, date bounds, duplicates, replay/corrections, manual-history guards, cancelled-payment restrictions, cross-booking/owner isolation, atomic rollback, receipt immutability, MFA and anonymous denial. Production smoke checks use rolled-back synthetic records. Browser screen verification remains unavailable due the credential-session blocker.
